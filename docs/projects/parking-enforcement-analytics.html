Parking Enforcement Analytics

Building a reproducible analytical pipeline from messy operational enforcement data to decision-ready BI — and being honest about where the data can and can't be trusted.

GitHub Repository
Problem
Fragmented enforcement exports, unaudited for quality
Data
~458K real operational scan-car events, anonymized
Methods
dbt marts, SARIMA forecasting, data validation
Output
Power BI dashboard + 15 passing dbt tests
01 — The Problem
Can this operational data actually be trusted?

A former employer's parking enforcement operation produced scan-car exports — detailed single-day logs, multi-day rollups, and workflow records — with no existing audit of whether the data was internally consistent or fit for reporting. The question wasn't just "what does the data say," but whether it could support reliable performance and coverage reporting at all.

02 — The Data
Real operational data, strict anonymization
  • Source: real scan-car enforcement data from a former employer — operational, not public/synthetic.
  • Scale: approximately 458,000 enforcement events across a one-day detailed source, ~2.5 years of multi-day rollups, and a richer workflow-detail source.
  • Anonymization: operators hashed to opaque tokens, zone codes shuffled to Zone_NNN labels via a git-ignored mapping file — engineered as a hard architectural constraint, not a post-hoc scrub.
  • Limitation: single export window — trends near the end of the data can't be distinguished from real operational change (see Limitations).
03 — What I Built
Ingestion → warehouse → marts → BI
Python ingestion + anonymization → Parquet → DuckDB → dbt staging → dimensional marts → Power BI

Staging models normalize three source formats (stg_events_day1, stg_events_multiday, stg_trigger_taxonomy, stg_scan_report) into a unioned fact table (fct_enforcement_events), feeding marts for hourly/daily zone activity, unit performance, operator funnel, and review turnaround.

04 — Approach
The judgment calls, not the tool list
  • Overlapping cumulative exports required verifying true duplicates rather than blindly dropping rows that looked identical.
  • Near-identical events in the single-day source were confirmed as legitimately separate occurrences, not deduplication artifacts — avoiding a silent undercount.
  • Anonymization was designed as an architectural constraint from the start (hashed operators, shuffled zones, git-ignored mapping) rather than a checkbox applied at the end.
05 — Key Findings
What the data actually showed
FINDING 01
Review funnel: 12,327 scans → 461 flagged → 43 escalated, with skewed turnaround times across the review pipeline.
FINDING 02
Fleet-wide map-coverage gap of 5.2–11.5%, varying by enforcement unit.
FINDING 03
Workload was concentrated on one operator rather than distributed evenly across the review team.
FINDING 04
Peak enforcement load reached 855 events/minute.
06 — Validation & Quality
How reliability was tested
  • 15 passing dbt tests across staging and mart models.
  • A full pipeline rebuild was completed and verified with zero errors.
  • SARIMA forecast treated cautiously: the model was not presented as production-ready.
07 — Limitations
  • The observed decline in the forecast window could reflect the data-collection window ending rather than a genuine drop in enforcement activity — stated explicitly rather than hidden.
  • The forecast's confidence interval extends below zero for count data, a known statistical artifact flagged rather than papered over.
  • The dataset covers one operational deployment; findings may not generalize to other fleets or cities.
